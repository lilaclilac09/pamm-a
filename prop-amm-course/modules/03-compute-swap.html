Your Weapon: compute_swap

One function. Six inputs. One output. This is where you win or lose the challenge.

What your function receives and returns

// The full contract you must implement
pub fn compute_swap(data: &[u8]) -> u64 {
// Deserialize to get these fields:
side: u8, // 0 = buy X, 1 = sell X
input_amount: u64, // tokens trader sends in
reserve_x: u64, // AMM pool of token X
reserve_y: u64, // AMM pool of token Y (the numeraire)
storage: [u64; 1024], // your persistent memory
// Must return: how many tokens the AMM gives to the trader
}
side

Buy X (trader sends Y) or sell X (trader sends X). Tells you which direction the swap goes.

reserves

Current reserves in the pool. Dividing them gives you the AMM's current spot price.

storage

1024 u64 slots that persist across every trade. Use them to track volatility, recent prices, or any state you need.

Two rules you must never break

The simulation assumes your function satisfies two mathematical properties. Violate them and the arb / router math breaks down.

Rule 1: Monotonic

output(input=10) > output(input=5)
output(input=5) > output(input=1)

More tokens in must always yield more tokens out. If this breaks, arb search algorithms fail to find the optimal trade and the simulation gives wrong results.

Rule 2: Concave

marginal_output(Δ=11) < marginal_output(Δ=10)
marginal_output(Δ=10) < marginal_output(Δ=5)

The rate of output must slow down as input grows. A linear function is the edge case; you must be strictly concave or you create arbitrage exploits against yourself.

Why the constant-product formula satisfies both rules
f(Δ) = (ry × Δ) / (rx + Δ)
// First derivative (always positive → monotonic):
f'(Δ) = rx × ry / (rx + Δ)² > 0 ✓
// Second derivative (always negative → concave):
f''(Δ) = −2 × rx × ry / (rx + Δ)³ < 0 ✓

The afterSwap callback: your memory

After each trade executes, the simulation calls afterSwap, giving you a chance to update your storage. This is how you build memory — track recent prices, estimate volatility, count trades, or update your fee model.

CODE 

pub fn after_swap(data: &[u8])
    -> [u64; 1024] {
  let d = deserialize(data);
  let mut s = d.storage;
  // s[0] = trade count
  s[0] += 1;
  // s[1] = last input amount
  s[1] = d.input_amount;
  // s[2] = last output amount
  s[2] = d.output_amount;
  s // return updated storage
}
PLAIN ENGLISH

after_swap fires after every trade and returns the new storage array.

Deserialize the callback data — it contains the same swap fields plus the actual output_amount.

Take a mutable copy of the current storage (1024 slots of u64).

Increment a trade counter in slot 0 — you now know how many trades have happened.

Remember the last input and output. Next call to compute_swap can read these from storage.

Return the updated storage. These values survive into the next compute_swap call.

Idea 1
Rolling Volatility

Store recent reserve ratios and compute implied vol. Widen fees when markets are moving fast.

Idea 2
Flow Imbalance

Count buy vs sell orders. If orders are heavily one-sided, price is trending — raise fees.

Idea 3
Virtual Liquidity

Pretend you have more reserves than you do. Flatter curves attract more retail flow — at the cost of more arb exposure.

Under the hood: BPF execution

Your Rust code compiles to BPF bytecode and executes inside a virtual machine. The executor loads your compiled program, passes the swap data as input bytes, and reads back the u64 output. This is exactly how Solana programs run on-chain.
