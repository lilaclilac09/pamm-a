What is an AMM?

You're about to build a market-making robot. Let's understand what that actually means.

Markets need someone to make prices

🏦

Traditional Exchange

Buyers and sellers post limit orders. A centralized order book matches them when prices cross. Requires active human market makers.

🤖

Automated Market Maker

A AMM uses a mathematical formula to quote prices 24/7. No humans needed — just math and liquidity.

When you trade on Uniswap or any DeFi exchange, you're not matched with another human. You're trading directly against a pool of tokens managed by an AMM formula.

The AMM has two buckets of tokens

The classic constant-product AMM demands that reserve_x × reserve_y always equals the same number k. This single rule determines every price the AMM quotes.

// How many Y tokens do you get for Δx tokens of X?
// Before: rx × ry = k
// After:  (rx + Δx) × ry_new = k
output_y = ry − (k / (rx + Δx))
output_y = (ry × Δx) / (rx + Δx)
// Bigger input → bigger output, but with diminishing returns

Price emerges from the ratio

The spot price of token X in terms of Y is just reserve_y / reserve_x. When the pool has 1,000 X and 2,000 Y, one X costs about 2 Y. No oracle needed — the ratio is the price.

Before Trade
X=1000, Y=2000
Price = 2.00 Y/X
Someone Buys 100 X
Pays ≈ 182 Y
Price impact: paid 1.82/X avg
After Trade
X=900, Y=2182
Price = 2.42 Y/X

That price increase is not a bug — it's a feature. Large buyers pay more, which deters excessive single trades and ensures the AMM always has tokens to sell. The curve is concave by design.

The starter code, decoded

This is the actual Rust you start with. It implements a basic constant-product AMM with a 5% fee. Let's read it line by line.

CODE 

pub fn compute_swap(data: &[u8]) -> u64 {
  let decoded = wincode::deserialize(data);
  let input = decoded.input_amount as u128;
  let rx    = decoded.reserve_x    as u128;
  let ry    = decoded.reserve_y    as u128;
  let fee_input = input * 9500 / 10000;
  ((ry * fee_input) / (rx + fee_input)) as u64
}
PLAIN ENGLISH

The function receives the full market state as raw bytes and returns how many tokens to give out.

Decode the bytes into a struct with input_amount, reserve_x, reserve_y fields.

Unpack the input amount and both reserves into 128-bit integers to avoid overflow.

Charge a 5% fee: multiply input by 9500/10000, so only 95% of the input counts toward the swap.

Apply the x*y=k formula using the fee-adjusted input. Return as a 64-bit integer.

Your challenge: replace this formula with something smarter. The fee, the shape of the curve, even the state you track — all of it is under your control. The next modules explain what "smarter" means.

10,000 steps. Prices drift. Predators attack. Customers arrive. Here is every frame of that battle.

Meet the four players

📈
Price Process

The "GBM" random walk. Each step, the fair price of token X drifts up or down by a random amount. This is the ground truth that other actors react to.

🦈
Arbitrageur

The predator. After every price move, the arbitrageur computes the optimal trade to extract maximum profit from any gap between your AMM price and the new fair price.

🛍️

The customer. Arrives each step with a random order (buy or sell). The router compares your AMM against the normalizer and sends the order wherever the trader gets a better deal.

⚙️
Your AMM

Your formula. You receive every trade and decide how many tokens to give out. Your goal is to earn more from retail spread than you lose to arb — across every step of every market.

Your Weapon: compute_swap

One function. Six inputs. One output. This is where you win or lose the challenge.

What your function receives and returns

// The full contract you must implement
pub fn compute_swap(data: &[u8]) -> u64 {
// Deserialize to get these fields:
side: u8, // 0 = buy X, 1 = sell X
input_amount: u64, // tokens trader sends in
reserve_x: u64, // AMM pool of token X
reserve_y: u64, // AMM pool of token Y (the numeraire)
storage: [u64; 1024], // your persistent memory
// Must return: how many tokens the AMM gives to the trader
}
side

Buy X (trader sends Y) or sell X (trader sends X). Tells you which direction the swap goes.

reserves

Current reserves in the pool. Dividing them gives you the AMM's current spot price.

storage

1024 u64 slots that persist across every trade. Use them to track volatility, recent prices, or any state you need.

Two rules you must never break

The simulation assumes your function satisfies two mathematical properties. Violate them and the arb / router math breaks down.

Rule 1: Monotonic

output(input=10) > output(input=5)
output(input=5) > output(input=1)

More tokens in must always yield more tokens out. If this breaks, arb search algorithms fail to find the optimal trade and the simulation gives wrong results.

Rule 2: Concave

marginal_output(Δ=11) < marginal_output(Δ=10)
marginal_output(Δ=10) < marginal_output(Δ=5)

The rate of output must slow down as input grows. A linear function is the edge case; you must be strictly concave or you create arbitrage exploits against yourself.

Why the constant-product formula satisfies both rules
f(Δ) = (ry × Δ) / (rx + Δ)
// First derivative (always positive → monotonic):
f'(Δ) = rx × ry / (rx + Δ)² > 0 ✓
// Second derivative (always negative → concave):
f''(Δ) = −2 × rx × ry / (rx + Δ)³ < 0 ✓

The afterSwap callback: your memory

After each trade executes, the simulation calls afterSwap, giving you a chance to update your storage. This is how you build memory — track recent prices, estimate volatility, count trades, or update your fee model.

CODE 

pub fn after_swap(data: &[u8])
    -> [u64; 1024] {
  let d = deserialize(data);
  let mut s = d.storage;
  // s[0] = trade count
  s[0] += 1;
  // s[1] = last input amount
  s[1] = d.input_amount;
  // s[2] = last output amount
  s[2] = d.output_amount;
  s // return updated storage
}
PLAIN ENGLISH

after_swap fires after every trade and returns the new storage array.

Deserialize the callback data — it contains the same swap fields plus the actual output_amount.

Take a mutable copy of the current storage (1024 slots of u64).

Increment a trade counter in slot 0 — you now know how many trades have happened.

Remember the last input and output. Next call to compute_swap can read these from storage.

Return the updated storage. These values survive into the next compute_swap call.

Idea 1
Rolling Volatility

Store recent reserve ratios and compute implied vol. Widen fees when markets are moving fast.

Idea 2
Flow Imbalance

Count buy vs sell orders. If orders are heavily one-sided, price is trending — raise fees.

Idea 3
Virtual Liquidity

Pretend you have more reserves than you do. Flatter curves attract more retail flow — at the cost of more arb exposure.

Edge: The Profit Formula

Every trade makes you money or costs you money. Here is the exact math that determines which.

Edge = what you earn at fair value

Edge is not the same as cash profit. It is the profit you made if every token were immediately valued at its current fair price. This matters because the simulation resets at fair value each step — you cannot let tokens accumulate at stale prices.

+

Retail Trade Edge

// AMM sells X to trader
edge = amount_y_in
- amount_x_out × fair_price

You received Y. You gave away X. Your spread is the gap between the Y you got and what that X was worth at fair price. This is positive when your fee > 0.

−

Arb Trade Edge

// AMM buys X at stale price
edge = amount_x_in × fair_price
- amount_y_out

The arb paid you too little Y for too much X. You overpaid for X relative to its fair price. This is always negative — adverse selection is unavoidable.

Net Edge = Retail Spread − Arb Losses

Win the challenge by making this number bigger than the normalizer's. You can do it by earning more retail spread, losing less to arbs, or both.

The exact edge calculation from the source

CODE 

// From engine.rs
let trade_edge = if trade.amm_buys_x {
  trade.amount_x * fair_price
    - trade.amount_y
} else {
  trade.amount_y
    - trade.amount_x * fair_price
};
submission_edge += trade_edge;
PLAIN ENGLISH

For every single trade that touches your AMM, this formula runs.

If your AMM is buying X (trader sells X to you): value received = amount_x × fair_price. Subtract amount_y you paid. This is the arb scenario — usually negative.

If your AMM is selling X (trader buys X from you): value received = amount_y. Subtract amount_x × fair_price — what that X was actually worth. This is the retail scenario — usually positive.

Accumulate edge across all 10,000 steps. This single running total is your final score.

Worked example

Fair price: 2.00 Y/X
Arb sells 50 X, gets 98 Y
Edge = (50 × 2.00) − 98
Edge = 100 − 98 = +2.0
Wait — arb edge is positive for arb.
For YOU: −2.0
Retail trade (good for you)
Fair price: 2.00 Y/X
Trader sends 20 Y, gets 9.5 X
Edge = 20 − (9.5 × 2.00)
Edge = 20 − 19.0 = +1.0
You kept 1 Y worth of spread.
+1.0 to your score.

The fundamental tension

There is a brutal tradeoff at the heart of every AMM. Higher fees protect you from arbs — but also drive retail traders to the normalizer instead.

Low fee
e.g. 10 bps
✓ Attracts max retail flow
✗ Tiny spread per trade
✗ Bleeds badly to arbs
Sweet spot
depends on market
✓ Competitive with normalizer
✓ Enough spread to cover arbs
↑ Varies by vol, flow, opp fee
High fee
e.g. 300 bps
✓ Arb losses stay small
✗ No retail trades routed to you
✗ Zero spread revenue

The optimal fee is not fixed — it depends on current volatility, retail flow intensity, and what the normalizer is charging. Static fees leave money on the table. The best strategies adapt.

The arbitrageur is not evil — it is doing what rational actors do. Here is the economic logic.

🦈

🦈

05

Strategy Space

Dynamic fees. Virtual reserves. Adaptive curves. Here is what separates a good AMM from a great one.

Three axes of innovation

The starter code is a static 5% fee constant-product AMM. Any single improvement can beat it. The best submissions combine all three axes.

📐

Axis 1: Curve Shape

The constant-product formula is just one valid concave curve. You can use a concentrated liquidity design (tighter curve in a price band), a stableswap-style flat curve, or your own custom function. Flatter curves attract more retail volume by offering lower slippage.

⚡

Axis 2: Dynamic Fees

A fixed fee is sub-optimal almost by definition. In volatile markets, a higher fee covers your arb losses. In calm markets, a tighter fee steals more retail flow. Reading the storage to estimate current volatility and adjusting your fee accordingly is one of the highest-leverage improvements you can make.

🧠

Axis 3: State & Memory

The 1024-slot storage is your unfair advantage. A stateless AMM is flying blind. Track reserve ratios across recent steps to estimate realized volatility, detect trending markets, or count buy/sell imbalance. Each observation makes your next trade more informed.

A dynamic fee implementation, decoded

Here is one concrete way to adapt your fee to estimated market volatility using the storage buffer.

CODE 

pub fn compute_swap(data: &[u8]) -> u64 {
  let d = deserialize(data);
  // Read estimated vol from storage
  let est_vol = d.storage[0];
  // Scale fee: base 30bps + vol term
  let fee_bps = 30 + est_vol / 100;
  let scale = 10000 - fee_bps;
  let fi = d.input_amount * scale / 10000;
  let rx = d.reserve_x as u128;
  let ry = d.reserve_y as u128;
  ((ry * fi) / (rx + fi)) as u64
}
PLAIN ENGLISH

Start by deserializing — same as always.

Read slot 0 of storage. Some earlier call to after_swap put an estimated volatility measure here (e.g. in units of 1/10000).

Dynamic fee = a 30 bps floor plus a vol-proportional top-up. In calm markets: ~30 bps. In wild markets: higher.

Convert fee to a multiplier: 10000 minus fee in bps. Apply to input to get the fee-adjusted swap amount.

Run the standard constant-product formula with the dynamic fee_input. Higher vol = higher fee = less output to trader = more protection for you.

Virtual reserves: fake it to attract it

Instead of using your actual reserve sizes, you can swap against inflated "virtual" reserves. This makes your curve flatter — lower price impact — attracting more retail volume at the cost of tighter margins.

Real reserves
rx = 1000, ry = 2000
// For 20Y input:
out = (2000×20)/(1000+20)
out = 39.2 X

Price impact of 20Y trade: ~1.0%. The standard curve.

Virtual reserves (2×)
rx = 2000, ry = 4000
// For 20Y input:
out = (4000×20)/(2000+20)
out = 39.6 X

Price impact: ~0.5%. Trader gets 0.4 more X. They prefer this AMM. You win the flow.

The catch: virtual reserves also amplify arb losses. A flatter curve means arbs can extract more value per dollar of price move. You must pair virtual reserves with a higher dynamic fee to stay net-positive.

What actually works

The challenge runs across 1,000 markets with wildly different parameters. Strategies that are locally optimal (great for one market type) often fail globally. Robustness matters as much as peak performance.

Strategies that tend to work
  • ✓ EMA-based vol estimation with fee response
  • ✓ Moderate virtual reserves (1.2× to 1.8×)
  • ✓ Fee floors to avoid getting wiped on vol spikes
  • ✓ Being just slightly cheaper than the normalizer
Common traps
  • ✗ Static fees (the starter template)
  • ✗ Too-aggressive virtual reserves without higher fees
  • ✗ Over-fitting to one volatility regime
  • ✗ Breaking monotonicity or concavity
